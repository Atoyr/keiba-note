# uma-memo の評価 — Evaluator が見ること

変更を書いたエージェント（Generator）とは**別の**エージェント（Evaluator）が、
できあがったものを評価するための基準と手順。

- **読む場面:** Evaluator として評価するとき。Generator が PR を出す前に、評価を頼むとき
- **ここに無いもの:** 機械で止める検査（型・lint・E2E・画面カタログ）は [testing.md](./testing.md)、
  見た目の決まりは [design-system.md](./design-system.md)、何を作るかは [product.md](./product.md)、
  なぜ Generator と Evaluator を分けるかは [harness.md 第6層](./harness.md)
- 作成日: 2026-09-23

---

## 1. 役割の分け方

| | Generator | Evaluator |
| --- | --- | --- |
| やること | 指示を読んで実装し、テストとキャプチャを用意する | 指示の原文と成果物だけを見て、第3章の観点で評価する |
| 受け取るもの | 指示、コード、文書 | **指示の原文**・差分・after のキャプチャ・この文書 |
| 受け取らないもの | — | **Generator の説明や意図の解説**（それを読むと Generator と同じ見方になる） |
| 書き換え | する | **しない**（読むだけ。直すのは Generator） |
| 合否 | 自分で付けない | 付ける |

書いた本人は「こう作ったつもり」を知っているので、自分の画面を甘く読む。
評価を別の文脈（別のエージェント・別のセッション）に出すのは、その「つもり」を持ち込ませないため。

## 2. 手順

1. Generator が `pnpm run verify` を通し、`pnpm run screens <機能名> after` を撮る（機械で見られるものを先に済ませる）
2. Generator が Evaluator を起動し、次の4つだけを渡す
   - 指示の原文（issue の本文か、依頼の文そのまま。要約しない）
   - 差分（`git diff origin/main...HEAD`）
   - after と before のキャプチャのパス（`docs/screenshots/<機能名>/`）
   - この文書
3. Evaluator が第3章の観点ごとに判定し、第4章の形で返す
4. Generator は `✗` を直し、もう一度 1 から回す。**やり取りは2往復まで。** 残った `✗` と `?` は
   PR 本文の「評価」に載せ、人の判断に回す
5. Evaluator の指摘をそのまま採らない。Generator は指摘ごとに、キャプチャかコードで事実を確かめてから直す

Claude Code では `.claude/agents/evaluator.md` のサブエージェントとして起動する。
ほかのエージェントでは、新しいセッションを開いて上の4つとこの文書を渡す。

## 3. 観点

判定は `✓`（満たす）・`✗`（満たさない）・`—`（この変更に関係しない）・`?`（確かめられなかった）の4つ。
**確かめていないものを `✓` にしない。** 見られなかったら `?` にし、何を見れば確かめられるかを書く。

「機械」の列は、すでに機械で見ているもの。Evaluator はそこを繰り返さず、機械が見られない部分を見る。

### Functional — 動くか

| 観点 | 見ること | 機械 |
| --- | --- | --- |
| 操作できるか | 指示にある操作が、画面の上で最後までできるか。JavaScript が無くても送れるか | E2E（その操作のテストがあれば） |
| error state | 入力の誤り・他人のもの・無いもの・DB に届かないときに、何が起きて次に何をすればよいかが文で出るか。**`src/routes/+error.svelte` は今は無い**（SvelteKit の既定の画面になる） | 認可の E2E（出るかどうかだけ） |
| loading state | 送信中に二重に押せないか、押したことが分かるか（`use:enhance` の送信中） | なし |
| 空の state | 0件のとき（メモ0件、出走馬0頭）に次に何をすればよいか分かるか | 画面カタログ（seed に空の行があれば） |

### Accessibility — 誰でも使えるか

| 観点 | 見ること | 機械 |
| --- | --- | --- |
| keyboard 操作 | Tab だけで主な操作に届き、順番が見た目の順と合っているか。メニュー（`⋯`）が Esc で閉じるか | なし |
| label | 入力に `Label` か `aria-label` があるか。アイコンだけのボタンに名前があるか | なし（axe を入れる予定 → [harness.md 5-3](./harness.md)） |
| contrast | 文字と背景のコントラストが 4.5:1 以上か（大きい文字は 3:1）。`text-muted-foreground` を薄い面に重ねていないか | なし（同上） |
| focus | フォーカスが見えるか（`ring`）。送信やメニューのあとにフォーカスが迷子にならないか | なし |
| 色だけに頼らない | 枠・印・グレード・状態を色だけで区別していないか | なし |

### Design — 揃っているか

| 観点 | 見ること | 機械 |
| --- | --- | --- |
| hierarchy | その画面でいちばん大事なもの（主な操作・主な情報）がいちばん目に入るか。見出しの段が意味と合っているか | なし |
| spacing | 余白が Tailwind の既定の段だけでできていて、同じ関係のものは同じ間隔か | なし（lint を入れる予定） |
| consistency | 同じ意味のものが、他の画面と同じ部品・同じ見た目か（[design-system.md 第4章](./design-system.md)） | なし（同上） |
| density | 390px で主な操作が最初の1画面に入るか。詰め込みすぎて押し間違えないか（押せるものは24px 四方以上） | 画面カタログ（横のはみ出しだけ） |

### Product — 頼まれたものか

| 観点 | 見ること | 機械 |
| --- | --- | --- |
| goal を満たすか | 指示の原文にある「できるようになること」が、キャプチャとコードで確かめられるか。受け入れ条件があれば1つずつ | なし |
| 不要な機能を足していないか | 頼まれていない画面・ボタン・設定・文言が増えていないか。「ついでの改善」が混ざっていないか | なし |
| 原則に反していないか | 既定は閉じる（他人のメモが出ない）、毎回踏む導線だけ出しっぱなし、など（[product.md](./product.md)） | 認可の E2E（出ないことだけ） |

## 4. 返す形

```markdown
### 評価（Evaluator）

対象: <機能名> / 指示: <原文の1行目>

| 観点 | 判定 | 根拠 |
| --- | --- | --- |
| Functional / error state | ✗ | race-review.mobile.png: 保存に失敗したときの文が出る場所が無い（+page.svelte:120） |
| Accessibility / label | ? | TagPicker の札に名前があるかはキャプチャでは見えない。DOM を読む必要がある |
| Product / 不要な機能 | ✓ | 差分は指示の2点だけ |

#### 直すべきもの（✗）
1. …

#### 確かめられなかったもの（?）
1. …（何を見れば確かめられるか）
```

- 根拠には、キャプチャのファイル名か `ファイル:行` を必ず書く。印象だけの指摘はしない
- `✓` は表から省いてよい。`✗` と `?` は省かない
- Generator はこの表を PR 本文の「評価」にそのまま貼る。直したものは `✗ → 直した` と書き換える
- 見出しは `###` から始める。PR 本文の `## 評価` の下に入るので、`##` にすると
  `scripts/check-pr-body.ts` が別の欄と読み、「評価」が空と判定される
