# uma-memo のコードレビュー — 分野ごとのレビュアー

PR を出す前に、変更したファイルの分野（YAML・SQL・フロント・AI プロンプト）ごとに、
書いたエージェントとは別のエージェント（レビュアー）にコードを読ませるための基準と手順。

- **読む場面:** PR を出す前にレビューを頼むとき。レビュアーとして読むとき。重さの規則を変えるとき
- **ここに無いもの:** できあがった画面と振る舞いの評価（Evaluator）は [evaluation.md](./evaluation.md)、
  機械で止める検査は [testing.md](./testing.md)、約束そのものは分野の文書（[architecture.md](./architecture.md)・
  [api.md](./api.md)・[frontend.md](./frontend.md)・[design-system.md](./design-system.md)・[data/README.md](../data/README.md)）、
  なぜ書き手と見る側を分けるかは [harness.md 第6層](./harness.md)
- 作成日: 2026-09-30

---

## 0. いつ頼むか

**PR を出す前に `pnpm run review:plan` を回し、重さが `—` でないレビュアーをすべて起動する。**
実装・データ・文書のどれでも同じ。どのレビュアーを起動するかは人やエージェントが選ばず、
差分から機械で決める（第2章）。選ばれなかったレビュアーは起動しない。

起動できない場合（サブエージェントを使えない環境など）は、PR 本文の「コードレビュー」に
`reviewer-<名前>: 未実施（理由）` と書き、[testing.md 1-2](./testing.md#1-2-検証を完了できないとき) に従って引き継ぐ。
理由を書くことはレビューの代わりにならない。

## 1. レビュアーと Evaluator の分け方

|                  | レビュアー（4つ）              | Evaluator                                     |
| ---------------- | ------------------------------ | --------------------------------------------- |
| 見るもの         | コード・データ・指示文そのもの | できあがった画面と振る舞い                    |
| 物差し           | 分野の約束（第4章）            | Functional / Accessibility / Design / Product |
| 起動するかどうか | `review:plan` が差分から決める | [evaluation.md 第0章](./evaluation.md)        |

どちらも、別の文脈で読み、ファイルを書き換えず、Generator の説明や意図の解説を受け取らない
（書いた本人の「こう作ったつもり」を持ち込ませないため）。両方が要る変更では、並行で起動してよい。

| レビュアー    | エージェント        | 見るもの                                                                                             |
| ------------- | ------------------- | ---------------------------------------------------------------------------------------------------- |
| YAML          | `reviewer-yaml`     | `data/races/`・`data/examples/`（出走馬データ）、`.github/workflows/`（CI と自動実行）、YAML を書くスクリプト |
| SQL           | `reviewer-sql`      | `schema.ts`・`drizzle/*.sql`・サービス層・`auth/`・投入とオッズの SQL を組むスクリプト・seed          |
| フロント      | `reviewer-frontend` | `src/routes/`・`src/lib/components/`・`schemas/`・`utils/`・`hooks.server.ts`・`app.html`・E2E        |
| AI プロンプト | `reviewer-prompt`   | `AGENTS.md`・`CLAUDE.md`・`.claude/`（エージェント・スキル・設定）・`docs/`・`data/README.md`・PR テンプレート |

どれにも当たらないファイル（`package.json`・`wrangler.toml` など）は、`review:plan` が名前を出す。
人が見るか、Claude Code の `/code-review` に回す。

## 2. 重さ

レビュアーごとに、変更の中身から重さを決める。重さで、起動するモデル・見る範囲・指摘の扱いが変わる。

| 重さ | モデル（Claude Code） | 見る範囲                                                                                    | `必須` の指摘の扱い                                                        |
| ---- | --------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 重   | `opus`                | 第4章の観点をすべて。差分の外まで追う（呼び出し元・同じ表を読むほかの関数・関連するテスト） | 正しいと確かめた `必須` を直すまで PR を Ready にしない。2往復で直らなければ Draft にして人に回す |
| 中   | `opus`                | 第4章の観点をすべて。差分と、差分が直接呼ぶもの                                             | 直すか、直さない理由を書く（Ready にしてよい）                            |
| 軽   | `sonnet`              | 第4章の ★ の観点だけ                                                                        | 中と同じ。★ 以外の気づきは `参考` に留める                                 |
| —    | 起動しない            | —                                                                                           | —                                                                          |

どの重さでも、事実を確かめて誤りと分かった指摘は採らなくてよい。直さない理由は、どれも結果の表に
`必須 → 採らない（理由）` と書く（第3章の6）。人が判断すべきものは「レビューで見てほしいところ」にも挙げる。

### 決め方 — `scripts/review/rules.ts`

`review:plan` は差分の各ファイルを規則に当てる。規則は**パス**と、任意で**変わった行の中身**
（追加した行・消した行を分けられる）で当たる。レビュアーの重さは、当たった規則のうちいちばん重いもの。

- **中身で上げる。** 例: サービス層は中、`author_id`・`viewerId`・`visibility` に触れた行があれば重。
  `data/races/` は中、`withdrawn:` を足した・`ref:` を消した・`entries:` を空に戻したなら重。
  `.claude/agents/` は中、`tools:` の行に触れたら重
- **下げる。** テストだけのファイルと、コメントと空行だけの変更は、何に当たっても軽まで（本番の挙動は変わらない）
- **見せない。** 生成物（`drizzle/meta/`・コース図の SVG）・`pnpm-lock.yaml`・キャプチャ

規則の一覧は `rules.ts` が正。ここには写さない。

### 人が重さを変える

```bash
pnpm run review:plan --weight sql=重            # 規則より重くする
pnpm run review:plan --weight frontend=—        # 起動しない（理由を必ず書く）
```

変えた重さは表に「規則では〇。人が変えた」と出る。上げるのに理由は要らない。
**下げたときは理由を書く。** `—` にして起動しなかったレビュアーは、「コードレビュー」に
`reviewer-<名前>: 未実施（重さを下げた理由）` と書く。CI は規則どおりの重さで見るので、この行が無いと落ちる（第6章）。

### 規則を変える

同じ見落としが2回あったら、規則を足すか重さを上げる（[harness.md 6-4](./harness.md)）。
`rules.ts` を直し、`scripts/review/plan.spec.ts` に「この変更ならこの重さ」の例を1つ足す。
逆に、いつも重になって指摘が出ない規則は、中身の条件を絞る。

## 3. 手順

1. `pnpm run verify` を通したあとで、`pnpm run review:plan` を回す。
   検証できない場合は [testing.md 1-2](./testing.md#1-2-検証を完了できないとき) に従い、確認できた範囲でレビューを頼む
2. 重さが `—` でないレビュアーを、表のモデルで**並行に**起動し、次の3つだけを渡す
   - 指示の原文（issue の本文か、依頼の文そのまま。要約しない）
   - `review:plan` の出力（重さ・理由・そのレビュアーの対象ファイル）
   - 基準のブランチ（既定は `origin/main`）
3. レビュアーが第4章の観点で読み、第5章の形で返す
4. Generator は指摘ごとに、コードか文書で事実を確かめてから直す。**指摘をそのまま採らない**（レビュアーも間違える）。
   採らなかったものは、理由を結果の表に書き足す
5. 直したら `verify` から回し直し、`必須` が出たレビュアーだけもう一度起動する。**やり取りは2往復まで**
6. PR 本文の「コードレビュー」に、`review:plan` の出力と各レビュアーの結果を貼る。
   直したものは `必須 → 直した`、採らなかったものは `必須 → 採らない（理由）` と書き換える

Claude Code では `.claude/agents/reviewer-*.md` のサブエージェントとして起動し、表の「起動」の `model` を渡す。
ほかのエージェントでは、新しいセッションを開いて `reviewer-*.md` の本文と、上の3つとこの文書を渡す。

## 4. 観点

**★ は軽でも見る観点。** 機械が見ているもの（型・lint・`data:check`・`docs:check`・単体テスト・E2E）は繰り返さない。
約束の中身は分野の文書が正で、ここには「何を見るか」だけを置く。

### 4-1. YAML

出走馬データは **`main` にマージした時点で本番に入る**（[data/README.md](../data/README.md)）。戻すには別の PR が要る。

| 観点 | 見ること |
| --- | --- |
| ★ 本番に入れてよいか | `data/races/` に架空の馬・テスト用の値・書きかけが無いか（見本は `data/examples/`）。データの PR にコードの変更が混ざっていないか |
| ★ 取り下げ | `withdrawn` に入った馬が、出馬表に無い馬だけか。出走馬行が消え、メモが近況メモへ移ることを PR 本文に書いているか。`entries` から消えただけで `withdrawn` に入っていない馬が無いか（YAML から消しても DB からは消えない） |
| ★ 同一性（ref） | 既存の `ref` を書き換えていないか。`ref` と `name` を1回で両方変えていないか（新しい馬ができる。[data/README.md「馬名を直す」](../data/README.md)） |
| ★ ワークフローの権限 | `permissions` が最小か。`secrets` と外から来る値（PR の本文・タイトル・ブランチ名）を `run:` に `${{ }}` で直に埋め込んでいないか（`env:` で渡す）。`pull_request_target` を使っていないか |
| ★ 本番に触る job | `--remote`・`deploy`・`wrangler secret` を叩く job が、`main` への push か人の起動でしか走らないか |
| レースの特定 | `date`・`course`・`raceNumber` が番組と合っているか。レース番号を 11R と決め打ちしていないか。`surface`・`distance`・`direction` がその場のコースとして在りうるか |
| 枠・馬番・結果 | 枠と馬番の対応が頭数の規則に合うか。結果を書いた頭数と着順の抜け・重複、1着のタイムがいちばん速いか |
| 申し送り用の枠 | `entries` を埋めたレースを `entries: []` に戻していないか（枠・馬番が消える） |
| 上書きの順番 | 古い開催日のファイルで馬の属性（厩舎・馬名）を書き換えていないか（最新の開催日のファイルが勝つ） |
| 列の追加との順番 | 新しい列を書くデータが、その列のマイグレーションより先に本番へ入らないか（`data-import.yml` はマイグレーションを流さない） |
| 自動実行の時刻 | `cron` が UTC で書かれ、意図した JST になっているか。`concurrency` で二重に走らないか |

### 4-2. SQL

| 観点 | 見ること |
| --- | --- |
| ★ 誰のデータか | メモ・推し・騎手のまとめを読む関数が `viewerId` を必須で受け、WHERE に入れているか。件数を数える JOIN で他人のメモを数えていないか。`visibility` を見るのが共有ページだけか（[api.md 第5章](./api.md)） |
| ★ 文字列で組む SQL | 投入・オッズの SQL（`scripts/import-races.ts`・`scripts/odds/store.ts`）と `sql.raw` で、値をエスケープの関数に通しているか。Drizzle の `` sql`...${値}` `` はパラメータになるが、`sql.raw` はならない |
| ★ マイグレーション | `schema.ts` と `drizzle/*.sql` が一緒に変わっているか（生成物を手で直していないか）。テーブルを作り直す形（`__new_`）で、外部キーの子（`note` など）が `ON DELETE CASCADE` で消えないか。既存の行が新しい NOT NULL・CHECK・UNIQUE に通るか |
| ★ 消す | `race_entry` やメモを消す経路が増えていないか（メモは `ON DELETE CASCADE` で道連れになる）。投入は冪等で、書かなかった値を `COALESCE` で残しているか |
| クエリの数 | 1リクエスト10以内か。ループの中で `await db` していないか。複数の書き込みを `batch()` にまとめているか（[architecture.md 7-1](./architecture.md)） |
| 索引 | WHERE・ORDER BY・JOIN の列に索引があるか。一覧が全件を読まないか（D1 は読んだ行で課金される） |
| 制約違反 | UNIQUE 違反を `isUniqueViolation` で `fail(409)` に振り替えているか |
| セッション | トークンを平文で保存していないか（SHA-256 のハッシュだけ） |
| テスト | 絞り込みを変えたなら、他人のメモが出ないことを単体テストで確かめているか |

### 4-3. フロント

Evaluator が画面の上で確かめること（操作できるか・見た目）は繰り返さず、コードの約束を見る。

| 観点 | 見ること |
| --- | --- |
| ★ 層の向き | `.svelte` や画面側の `.ts` が `$lib/server/**` を import していないか（型も）（[architecture.md 第2章](./architecture.md)） |
| ★ 認証と飛び先 | `PUBLIC_PATHS` を広げていないか。入力から受けた戻り先を `safeRedirect` に通しているか。他人のものと無いものを同じ応答（404）にしているか |
| ★ 生の HTML | `{@html}` にメモの本文など利用者の入力が流れていないか |
| ★ action の入力 | Valibot を通してから使い、失敗を `fail(400, { message })` で返しているか。行の構成（`entryId`）を DB から引いているか（[api.md 第4章](./api.md)） |
| Svelte 5 | 計算で出る値を `$derived()` で書き、`$effect()` をブラウザの API に触るときだけにしているか |
| フォーム | JavaScript が無くても送れるか。`use:enhance` の送信中・失敗の出し方が [frontend.md 第3章](./frontend.md) の形か（失敗はトーストにしない） |
| リンク | アプリ内のリンクを `resolve()` で組んでいるか |
| 見た目の約束 | パレットの色名（`gray-500`・`red-600`）・任意値（`[...]`）・素の `<button>` `<select>` `<textarea>` を新しく書いていないか。`components/ui/` を手で直していないか。[design-system.md 第6章](./design-system.md) の避けることに当たらないか |
| 状態の置き場 | モジュールスコープにリクエストごとの値を持っていないか |
| テスト | 部品のテストを隣に置いたか。画面や状態を足したなら `e2e/screens.ts` に足したか |

### 4-4. AI プロンプト

エージェントが読んで従う文（`AGENTS.md`・`CLAUDE.md`・`.claude/`・`docs/`）を、指示として読む。

| 観点 | 見ること |
| --- | --- |
| ★ 食い違い | 変えた約束が、ほかの文書・エージェントの定義・スキルと矛盾していないか。同じ知識を2か所に写していないか（片方だけ直されてずれる。[harness.md 7-3](./harness.md)） |
| ★ 権限 | エージェントの `tools` が役割に対して最小か（読むだけの役に `Edit`・`Write` を与えていない）。`.claude/settings.json` の allow が広すぎないか・deny を外していないか |
| ★ 取り消しにくい操作 | 本番の D1（`--remote`）・`wrangler secret`・`deploy`・force push を、エージェントが自分で叩く読み方ができないか |
| ★ 外から来た文 | netkeiba の HTML・PR や issue の本文・ツールの出力を、指示として扱わせる書き方になっていないか |
| 止まる条件と完了の条件 | いつ終わりで、いつ止めて人に聞くかが [AGENTS.md「目指す状態」](../AGENTS.md) と食い違わないか |
| 起動の判断 | サブエージェント・スキルの `description` だけで、いつ使うか（いつ使わないか）が決められるか |
| 曖昧な語 | 「適宜」「よしなに」「なるべく」のような、読む人で結果が変わる語が無いか。「よく考えて」のような指示を書いていないか（[harness.md 7-4](./harness.md)） |
| 文書の形 | 冒頭に「読む場面」「ここに無いもの」があるか。約束に理由が付いているか。まだ無いものを「まだ使えない」と書いているか |
| 返す形 | PR 本文に貼る形が `###` から始まるか（`##` だと PR 本文の欄の検査が別の欄と読む） |
| 写してはいけないもの | 例に実在のメールアドレス・本番のデータが無いか |

## 5. 返す形

```markdown
### コードレビュー（reviewer-sql・重）

対象: src/lib/server/services/notes.ts ほか 2 ファイル / 指示: <原文の1行目>

| # | 重要度 | 場所 | 指摘 | 根拠 |
| --- | --- | --- | --- | --- |
| 1 | 必須 | services/notes.ts:120 | listSharedNotes が viewerId を省略可能で受けている | api.md 第5章「誰のデータか」 |
| 2 | 推奨 | services/notes.ts:88 | ループの中で await しており、出走馬の数だけクエリが走る | architecture.md 7-1 |

#### 確かめられなかったもの（?）

1. 0019 のマイグレーションで既存の行が CHECK に通るか。本番の行の分布を見る必要がある

見た観点: 4-2 のすべて（該当なし: セッション）
```

- **重要度は3つ。** `必須`（直さないと壊れる・漏れる・約束に反する）・`推奨`（直したほうがよい）・`参考`（差分の外の気づき）
- 場所には `ファイル:行` を必ず書く。根拠には、分野の文書の章か、コードの事実を書く。印象だけの指摘はしない
- **確かめていないものを「問題なし」にしない。** 見られなかったら「確かめられなかったもの」に、何を見れば確かめられるかと一緒に書く
- 指摘が無ければ表の代わりに「指摘なし」と書き、「見た観点」は必ず書く（どこまで見たかを人が判断できるように）
- 良い点を並べない。見出しは `###` から始める（PR 本文の `## コードレビュー` の下に入る）

## 6. CI で見ていること

`.github/workflows/pr-body.yml` が PR の差分で `review:plan` と同じ計画を（`--weight` 抜きの、規則どおりの重さで）立て、
重さが `—` でないレビュアーごとに、PR 本文の「コードレビュー」に次のどちらかがあるかを見る（`scripts/check-pr-body.ts`）。
無ければ落とす。

- 結果の見出し `### コードレビュー（reviewer-sql・重）`
- 起動しなかった行 `reviewer-sql: 未実施（理由）`

計画の表には起動しないレビュアーの名前も並ぶので、名前が含まれるかだけでは見ない。
見るのは結果か理由があることだけで、中身の良し悪しは人が見る。
手元では `PR_BODY="…" REVIEW_BASE=origin/main pnpm run pr:check` で同じ検査を回せる（`REVIEW_BASE` が無いと欄が空でないかだけを見る）。

GitHub Actions が作る PR（`race-data-fetch.yml`）には、この検査が走らない（`GITHUB_TOKEN` で作った PR には
ほかのワークフローが走らない）。そちらは人がマージの前に見る。
